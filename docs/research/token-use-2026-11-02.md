# Token use: where an accepted task's Claude tokens go

> Research, non-normative (2026-11-02). Operator: "System uses too much token; it should be
> optimized and rethought." Evidence for [PROP-0023](../proposals/0023-worker-roles-and-token-budget.md).
> It extends the [lean core research](lean-core-2026-11-01.md), which measured time and attention;
> this note measures tokens. No code or policy changes here.

## How it was measured

From the live store (`~/.dsh/system/system.db`, opened read-only) on 2026-11-02, the 7 days before
08:30 UTC, at `dev` `737ca1ad`. Usage is each record's `own` part: the growth of its session since
the previous record (T361), so a resumed session's spend is counted once. Cost is the runtime's
API-equivalent estimate (`runtime-estimate`); the accounts are subscriptions, so it measures quota
drawn, not money paid. `system metrics --days 7` and `roster` were read the same day.

Almost all input is cache reads: a run's cost is its context size times its turns, not the work it
writes. Output is 0.4 % of the tokens.

## 3. Sessions grow, and every resume re-reads them

Agent runs per session over the week: 1 run 19 sessions, 2 runs 29, 3 runs 21, 4 to 6 runs 51,
7 to 12 runs 67. A session is resumed after an approval wait (a quarter of all runs ended on one,
[lean core §3](lean-core-2026-11-01.md#3-where-a-tasks-time-goes)) and for each fix round. A resumed
run re-reads the whole transcript on every turn, so a session's cost grows with the square of its
length. A frontier develop run's 25.7 M input over 25.6 turns is about 1 M tokens of context per
turn.

## 4. Prompt sizes

| Step | Prompt (k tokens, mean) | Max |

| develop | 3.6 | 7 |
| review (all kinds) | 28 to 34 | 112 |
| selfreview | 25 to 31 | 59 |

A review's prompt carries the diff and the review guides of the areas it touches. A fresh run starts
small: one-turn runs on a new session have a context of about 11 k tokens beyond nothing but a short
prompt (141 runs, minimum 11.1 k), so the fixed part (the runtime's system prompt and six tools) is
about 10 k. One-turn develop runs that resume a session start at 182 k or more. Each run also
makes one small side call on the economy model (25 k input, 21 output; 11 USD a week in all).

## 6. Live System run

`run_fab7b75f346d6d2d` (brainstorm; ChatGPT Web and the Gemini API) on the design under the
operator's decisions of 2026-11-02. ChatGPT's proposal: fresh bounded sessions with a compact
handoff; standard tier for build and repair whatever the risk, frontier only on evidenced
difficulty and preferably as a short planning step; website static review beside the executable
checks; agent review required for trust-boundary changes, for a packet that cannot hold the context,
and when the website reviewer reports too little evidence; remove self-review, routine whole-patch
re-review, and blanket verification. Its ranking by saving: review-loop removal, standard tier,
fresh sessions, website review, fewer failed attempts; the riskiest for quality is removing review
loops while moving review to website Workers. It proposed turn caps (build 16, repair 8, review 12),
a 50 k context ceiling for build, and a 6 USD API-equivalent cap per attempt, all as pilot values.

The Gemini API member's proposal agrees on the shape. It ranks savings differently:

1. A fix in a fresh session from a compact brief, never the author's resumed transcript (about
   half of Claude's spend).
2. A standard-tier build.
3. Review, spec, and docs on website and other agent Workers.
4. No self-review.
5. Turn caps.

It is stricter on limits: 12 build turns, 1 fix cycle, and 3.50 USD a task. It names the standard
default for build as the riskiest change for quality.

Both members put a fix in a fresh session and static review on website Workers.

**Outcome.** Both members voted for ChatGPT's proposal (O1), with high confidence: method
team-majority, decision `sha256:45497ce7a485617086453a0f9c72263bd55cbbbc15bc89eafa30714317811835`.
Gemini's ballot judged its own 12-turn and 3.50 USD caps too aggressive for non-trivial changes.
