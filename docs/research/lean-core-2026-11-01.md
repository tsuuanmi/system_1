## 1. Where the work goes

the work; Gemini Web waits on a site challenge, and ChatGPT's quota has no reading.

| Step | Served by | Note |

| review | Claude standard 76, frontier 67; Codex about 80 | |

The frontier tier is about 49 % of the API-equivalent cost. Review-type steps are 59 % of all
steps and writing 17 % ([model routing](model-routing.md#11-counts-and-ratios-m-d)).

## 2. The ledger counts resumed sessions again

`meteringFrom()` (`runtime-claude-agent-sdk/src/index.ts`) records `total_cost_usd`, `num_turns`,
and the summed `modelUsage` of each SDK result; `resources` stores each result under its own id and
sums them. The SDK documents that a resumed call's result reports the session's whole spend, and
that summing results double counts it
([cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). In the store, one
session's records grow monotonically (cost 4.49, 5.35, 6.42, ... 33.79; a 23-second, one-turn run
carries 92 M input tokens).

| 7 days | Summed as recorded | Each session's growth only |
|---|---|---|
| input tokens (cache reads included) | 23.4 B | 5.5 B |
| output tokens | 85.8 M | 21.1 M |
| API-equivalent cost | 8,176 USD | 2,094 USD |

Every figure built on the sum is about 3.9 times too high: cost per accepted result, the report's
usage, and a task budget's spent lines.

## 3. Where a task's time goes

| Measure | Value |
|---|---|
| task created to done (137 tasks) | median 1.6 h, p90 6.2 h |
| ready to landed (`metrics`) | median 1.8 h, p90 5.3 h |
| attempts per accepted result | 2.47 |
| a completed run, wall | median 37 min, p90 99 min |
| the same runs, an agent busy | median 26 min, p90 57 min |
| agent hours by step | develop 57.5, fix 40.4, every review-type step together about 15 |
| task goal and criteria | median 273 words, p90 466 |

**The gate ends a quarter of all agent runs.** 529 of the 540 failed agent runs are "stopped at its
Bash call, which waits for the operator's approval" (25 % of all runs over the week, 37 % on
2026-10-31). The gate is a PreToolUse hook on every tool call; on `ask` it returns `defer`, the SDK
ends the turn, and the engine resumes the session in a new run after the approval
([a deferred tool call](../design/workflow-engine.md#a-deferred-tool-call)). ADR-0039 chose this
because the `workers` seam has no waiting status, and named it to revisit. The live studio policy
(`studio-default` v7) holds no `commandRules`, so the project policy's rules for tests and
read-only checks (T326) are not in force: only about twelve exact argv commands run without asking.

## 6. External evidence

- **Waiting without ending the run.** A pending `canUseTool` callback "can stay pending
  indefinitely"; hook callbacks time out (600 s by default); `defer` is for a wait longer than the
  process can stay up ([user input](https://code.claude.com/docs/en/agent-sdk/user-input),
  [hooks](https://code.claude.com/docs/en/hooks)). The Codex SDK has no channel to answer an
  approval in a turn (it closes the CLI's stdin); its `approvalPolicy: never` makes a blocked
  command fail back to the model.
- **Sandboxing removes most prompts.** Sandboxed Bash can be auto-allowed; Anthropic reports 84 %
  fewer prompts ([sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)).
  System already runs a `workspace-write` run's Bash in the SDK sandbox, writes to the worktree
  only, no network, no unsandboxed escape ([ADR-0038](../decisions/adr/0038-confined-commands-for-claude-code-workers.md)).
- **Classifiers miss.** Claude's auto mode: 0.4 % false positives, 17 % false negatives on real
  overeager actions ([auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)).
- **Self-review is weak; an independent, verifying reviewer is better.** Self-repair gains are
  modest without stronger feedback ([Olausson et al.](https://arxiv.org/abs/2306.09896)); evaluators
  favour their own output ([Panickssery et al.](https://arxiv.org/abs/2404.13076)); a verification
  step keeps incorrect findings under 1 % in Anthropic's code review
  ([Claude blog](https://claude.com/blog/code-review)). No controlled study fixes the best number
  of reviewers (the research run, H2: insufficient).
- **Routing saves on general benchmarks.** FrugalGPT up to 98 %
  ([arXiv 2305.05176](https://arxiv.org/abs/2305.05176)), RouteLLM 35 to 85 %
  ([LMSYS](https://lmsys.org/blog/2024-07-01-routellm/)); not shown for coding pipelines (H3:
  insufficient), so the saving must be measured per accepted result.
- **Long sessions rot; fresh sessions with a handoff.** Performance falls as input grows
  ([Chroma](https://www.trychroma.com/research/context-rot)); for long-running agents, start fresh
  from a progress file and git state, one feature per session
  ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Task size.** Agent PRs that are not merged are larger and touch more files
  ([arXiv 2601.15195](https://arxiv.org/abs/2601.15195)); over 845 k PRs, size does not predict
  time to merge ([the research run](#how-it-was-measured), E35). Split by independent testability,
  not by line count (H4: insufficient for a size rule).

## 7. Choices the runs converged on

| Decision | Chosen | Why |
|---|---|---|
| A. approvals | A3: command rules in force, in-sandbox Bash allowed, an asked call waits in the live query, `defer` only past a bound | removes the cause of a quarter of all runs, keeps every exit from the sandbox gated |
| B. review | B2: checks and one other-family review in parallel, verify only a disputed blocking finding, at most two fix rounds, self-review off, heavy adds a second reviewer | review-type steps are 59 % of steps for weak marginal evidence |
| C. tiers | C2: fix, re-review, verify at standard; digest, tally, triage at economy; one tier up on a failed check or a second fix round | frontier is half the cost and is set by risk, not by the step |
| D. sessions | D2: a fix stays in the develop session within an attempt; each new attempt starts fresh from a handoff | continuity inside an attempt, no 90 M-token sessions across attempts |
| E. operator | E2: dispatch auto for an active project, light tier auto-lands on green checks and a clean review, normal tier on one batched merge, no remediation approval | three of the four large approval classes go |
| F. parking | F2: three small reversible changes by risk, a row off and frozen, deletion after 30 days unused | reversible; nothing the live install uses is touched |

A team review of the proposal's first draft (`run_523389e965124793`) refined two of them: A's
sandbox allowance became a policy rule under ADR-0038, with the policy's `forbid` and `ask` first,
and E's light-tier auto-land waits on the operator, because a merge always asks by D56 (ADR-0060).

The research run's caution stands: none of these is proven end to end. Each is switched, measured
against the week above, and kept only if quality holds.

## Adopted

Into [PROP-0022](../proposals/0022-lean-core.md): choices A3, B2, C2, D2, E2, F2 above, the
ledger's per-session growth, the baseline week, and the quality guard.

## Not adopted

- A model classifier before the operator (A4): its miss rate is too high for a gate.
- No review for the light tier (B4), and deleting unused parts outright (F3).
- A line-count limit on tasks: the evidence does not support one.
